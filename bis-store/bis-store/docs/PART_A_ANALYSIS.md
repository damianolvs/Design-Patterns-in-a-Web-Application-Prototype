## 7.1.4 — Singleton: Connection Manager

| Question | Your answer |
|---|---|
| **At exactly which line is it guaranteed that only one instance exists?** | Two lines of `01-singleton/lib/DatabaseConnection.ts` produce the guarantee together, and neither works alone. **Line 34** is the check — `if (!DatabaseConnection.instance) {` — and **line 35** is the only place in the entire project where `new DatabaseConnection()` is ever executed. Because that `new` sits inside the `if`, it can run at most once per process. But the check would only be a suggestion without **line 26**, `private constructor()`, which stops any other file from bypassing `getInstance()` and calling `new` itself. The single reference is held in the private static field declared on **line 18**. If I have to name one line it is **line 35**, the single point of creation, and I would immediately add that it is only *guaranteed* to be single because of line 26. |
| **What would happen if the constructor were public?** | Any module could write `new DatabaseConnection()` and receive a brand-new object, so the class would stop being a Singleton even though `getInstance()` still existed and still looked correct. In this prototype the symptoms would show up directly in the JSON from `/api/singleton`: `connectionId`, assigned on **line 27**, would be different on every call instead of staying fixed, and `queryCount`, declared on **line 23** and incremented on **line 42**, would reset to zero each time, because each object would count its own queries instead of accumulating into shared state. I verified the correct behaviour by calling the endpoint three times in a row: `connectionId` stayed `conn_ek1hdyc9` across all three and `totalQueries` went 1 → 2 → 3, which is the evidence that a single object is accumulating state. With a public constructor all three calls would have reported `totalQueries: 1` under three different ids. The dangerous part is that it fails *silently* — the code still compiles, the API still answers 200, and you only find out when two parts of the system disagree about what the state is. That is why the `private` keyword on line 26 matters more than the `if` on line 34: the `if` prevents an accident, the `private` prevents a bypass. |
| **Name a case in your own project where you would use Singleton.** | In my Part B prototype I used it for the `StoreState` class at `store/patterns/store_state.py` **lines 54–175**, which holds the catalogue, the shopping cart and the activity log in memory. Since the prototype has no database, every Django request has to reach the same object or the cart would reset on every click — the same "single per process" idea the teaching note on **lines 59–67** of `DatabaseConnection.ts` describes, applied to a Python process instead of a Node one. Outside this lab, what I would actually reach for in a Django project is a parsed configuration or feature-flag object: reading and validating settings is work you want to do exactly once at startup, and every module needs to see the same values. I would be careful about using it for a cart in production, though — a singleton is per process, so under Gunicorn with four workers you would get four independent carts. That is fine for a single-user prototype and wrong for a real shop. |

## 7.2.4 — Factory: Notification Factory

| Question | Your answer |
|---|---|
| **Which line decides which concrete class is instantiated?** | The `switch (type)` that opens on **line 56** of `02-factory/lib/notifications.ts`, inside `NotifierFactory.create()` which starts on **line 55**. The decision is made by its three branches: `case "email"` on **line 57** returning `new EmailNotifier()` on **line 58**; `case "sms"` on **line 59** returning `new SmsNotifier()` on **line 60**; and `case "push"` on **line 61** returning `new PushNotifier()` on **line 62**. The `default` on **line 63** throws on **line 67**, so an unrecognised type arriving from an HTTP request fails loudly instead of returning `undefined`. Lines 58, 60 and 62 are the only three places in the whole project where any notifier is constructed — the API route at `02-factory/app/api/factory/route.ts` **line 14** calls `NotifierFactory.create(type)` and never writes `new` itself. That is what makes this a Factory rather than a helper function: the caller has no dependency on the concrete classes at all, which are not even exported — they are declared without `export` on **lines 17, 28 and 40**, so nothing outside this file could instantiate them even if it wanted to. |
| **What would you need to change to add a WhatsApp channel?** | Three edits, all inside `02-factory/lib/notifications.ts`. **First**, write a `WhatsAppNotifier` class implementing the `Notifier` interface declared on **lines 11–14** — it needs a `channel` property and a `send(to, message)` method returning the same `{ channel, deliveredTo, detail }` shape, so it would sit with the others, around **line 49**. **Second**, widen the `NotificationType` union on **line 51** from `"email" | "sms" | "push"` to include `"whatsapp"`. This is the step people forget: without it TypeScript rejects the new value at the `create()` signature on line 55. **Third**, add `case "whatsapp": return new WhatsAppNotifier();` to the switch, between **lines 62 and 63** so it lands before the `default`. Then add one `<option>` to the `<select>` in `02-factory/app/page.tsx` so a user can pick it. What does **not** change is the point of the exercise: `app/api/factory/route.ts` stays byte-for-byte identical, because **line 14** already asks the factory for "a notifier of type X" and never knew the concrete classes existed. I confirmed the controlled-failure path on the running prototype by POSTing `{"type":"whatsapp"}` and getting back `{"ok":false,"error":"Unsupported notification type: whatsapp"}` with HTTP 400 — the `throw` on line 67 doing its job before the channel exists. |
| **Name a case in your own project where you would use Factory.** | The clearest case in a Django project I have worked on is exporting a report in several formats — PDF, CSV and XLSX. Each exporter has completely different internals but the same job: take a queryset, return a file. A `ReportExporterFactory.create(fmt)` keeps that decision in one place and the view just calls `.export(data)`, without importing three libraries it does not care about. A second case is payment gateways: Stripe, PayPal and Conekta all need `charge()` and `refund()`, and which one runs depends on configuration rather than on the checkout code. I considered adding a Factory to my Part B prototype and decided against it: my three shipping strategies are stateless and instantiated once at import time in the registry at `store/patterns/shipping.py` **lines 121–125**, so there is no construction complexity to centralise. A `ShippingStrategyFactory` would have been a class with a pattern's name on it and no actual work to do, which section 8.2 of the guide says is not accepted. |

## 7.3.4 — MVC: Task List

| Question | Your answer |
|---|---|
| **Which file(s) correspond to each layer (M / V / C)?** | **Model — `03-mvc/models/Task.ts`.** The `Task` interface on **lines 12–17** defines the shape, the in-memory array on **lines 20–24** is the "database", and the `TaskModel` object on **lines 26–59** holds the four data operations: `findAll()` at 27, `create()` at 31, `toggle()` at 42, `remove()` at 54. The file imports nothing at all — no `next/server`, no React, no request object. **Controller — `03-mvc/controllers/TaskController.ts`.** The `TaskController` object on **lines 15–44** receives intent, validates it, calls the Model and decides the status code. Its only import is the Model, on **line 13**. The validation on **lines 22–24**, where an empty title returns `{ ok: false, error: "Title is required", status: 400 }`, is the clearest example of logic that belongs here and nowhere else — the Model never sees an invalid title. **View — `03-mvc/components/TaskForm.tsx` and `03-mvc/components/TaskList.tsx`.** `TaskList` on **lines 12–38** receives `tasks`, `onToggle` and `onDelete` as props and renders them; `TaskForm` on **lines 12–33** renders an input and calls `onCreate`. Neither contains the string `fetch` anywhere. Two files are easy to mislabel. `03-mvc/app/api/tasks/route.ts` and `app/api/tasks/[id]/route.ts` are **not** the Controller — they are a thin HTTP front door, and each handler is two or three lines that parse the request and delegate immediately: `TaskController.list()` on **line 6** and `TaskController.create(body)` on **line 13** of `route.ts`; `TaskController.toggle()` on **line 6** and `TaskController.remove()` on **line 12** of `[id]/route.ts`. And `03-mvc/app/page.tsx` is not a pure View either — it is the client-side glue, and the only file in the project that calls `fetch`, on **lines 17, 27, 36 and 41**. |
| **What would happen if `TaskList.tsx` fetched directly?** | It would stop being a View. Right now it receives everything through the props signature on **lines 12–20**, which means it knows how to *display* a task list and nothing else. If it called `fetch("/api/tasks")` itself, four things would break. It would become coupled to that specific URL and response shape, so renaming the route would break a presentational component. It could no longer be reused anywhere the data came from somewhere else — a different endpoint, a parent that already holds the array, a test with a fixture. Testing it would require mocking the network instead of just passing an array of `Task`. And the round trip described in section 7.3.1 — View → API route → Controller → Model → View — would lose its single entry point, with fetching scattered across whichever components happened to need it. There is also a subtler problem specific to this prototype: `page.tsx` calls `loadTasks()` after every mutation, on **lines 32, 37 and 42**, so the whole list refreshes from one source. If `TaskList` fetched on its own, that single refresh point would be gone and the two components could end up showing different data at the same time. The rule the prototype follows is that only `app/page.tsx` knows the API exists; everything below it just renders what it is given. |
| **Name a case in your own project where you would use MVC.** | I used Django's MVT for my Part B prototype, which is the same idea under different names — the Template plays the View's role and Django's "view" plays the Controller's. In BIS Store the layers are `store/models.py` (Model: cart, weights, tax, totals, order building), `store/views.py` (Controller: validates input and delegates — the longest function in the file is 16 lines), and `store/templates/store/` (Template: renders, calculates nothing). More generally I would use it for any CRUD application meant to outlive one sprint: an inventory system, a booking system, a blog. The specific payoff I got is exactly the one stated in section 7.3.1 of the guide. My Model layer imports nothing from Django at all, and that is enforced by a test at `store/tests.py` **lines 111–125** which parses the file's AST and fails if a single `django.*` import ever appears. So swapping my hardcoded catalogue for a real database would not require touching a view or a template — the same claim the guide makes about replacing the in-memory array on lines 20–24 of `models/Task.ts`. |
